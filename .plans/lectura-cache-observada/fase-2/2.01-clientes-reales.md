# 2.01 Verificar el panel con cada cliente documentado

**Objetivo:** confirmar en Chrome la apariencia y los datos del panel viendo peticiones de los clientes reales, sin confundir esta comprobación con el replay de FULL.

**Lee:** `README.md` (Arranque, Copilot CLI y Certificados); `via.sh`; `scripts/check_copilot.py` (`reserve_ports`, `write_bootstrap`, `wait_for_dashboard`, `read_snapshot`, `stop_process`; no usar `run_real`); `tests/ui/check.mjs` (modo `--inspect-cache-read`).

**Puedes tocar:** `validacion-real.md` de este plan (nuevo); ficheros auxiliares fuera del repo en un directorio temporal propio. No cambies código del proyecto en esta tarea.

## Puerta de ejecución

- Esta tarea es **obligatoria para cerrar el plan**, pero no se ejecuta hasta que el usuario apruebe esta fase y su presupuesto: **una invocación por cliente de IA** (Copilot CLI, Claude Code y OpenCode), `hola` o `holi`, modelo barato explícito, sin reintentos ni sustituciones automáticas. Los scripts hacen solo llamadas a una API local simulada: coste cero. No se repite una llamada solo para forzar un HIT.
- Antes de lanzar nada pagado, el orquestador debe confirmar la cuenta/proveedor permitido, el modelo exacto disponible de Claude Code y de OpenCode, y que se pueden excluir herramientas/escrituras y el entorno de trabajo habitual. Verifica antes también la disponibilidad de `requests` y `httpx`; en los intérpretes comprobados al redactar no estaban instalados. Si faltan, solicita un entorno de prueba que ya los tenga o aprobación para instalarlos en un venv temporal separado, nunca en el del proyecto. Si falta autorización, un perfil, una dependencia o una credencial, marca esta tarea `bloqueada`. No leas ni copies secretos para suplirlo. No declares que un cliente real ha pasado usando solo la matriz de fixtures.

## Pasos

1. Prepara un proxy y un panel aislados con los helpers citados: puertos efímeros ajenos a 8899/8900, directorio y JSONL temporales, CA de confianza solo en los procesos de prueba. Si usas la CA existente para clientes autenticados, no la edites, exportes ni instales en el sistema. Guarda los resultados en el informe sin cabeceras, prompts de sistema, cuerpos crudos ni IDs privados. Ejecuta los CLI desde un workspace temporal vacío; no reinicies o reutilices los procesos habituales.
2. Usa la matriz siguiente. `via.sh` se llama por ruta absoluta con el `TAP_PROXY_PORT` de prueba, manteniendo el cwd temporal. Para Copilot, incluye los demás flags de aislamiento de `run_real`, omite `--auto-tier`, usa modelo explícito y `--reasoning-effort=low`. Para OpenCode verifica `opencode run --help` y usa `--standalone` para que el servidor comparta el entorno del proxy, sin `--auto`; el operador aporta un perfil temporal con política `tool.use` de denegación, sin MCP, plugins externos ni herramientas de escritura. Para Claude Code usa `-p`, `--tools ""`, `--strict-mcp-config`, `--no-session-persistence` y un perfil aislado aprobado; comprueba que no carga hooks o herramientas activos. No uses `--bare` como supuesto de acceso por suscripción. Si no puedes imponer estas condiciones con la instalación real, para antes de pagar esa fila.

   | Cliente real | Estímulo autorizado | Captura a verificar |
   | --- | --- | --- |
   | Copilot CLI en terminal de Orca | `holi`, `gpt-6-luna`, esfuerzo `low`, una invocación | Host Copilot, `/responses` por WebSocket, estado final `done`; el resumen CLI y la suma de filas coinciden si hay varias llamadas internas |
   | Claude Code | `hola`, Haiku de bajo coste con ID exacto aprobado, una invocación | `/messages` del proveedor aprobado y al menos una fila `done` con uso; si emite varias, distinguirlas sin informarlas como un solo resultado |
   | OpenCode | `hola`, modelo barato y proveedor configurados y aprobados, una invocación | Tráfico de inferencia del servidor privado por una ruta soportada y al menos una fila `done` con uso |
   | Script de Node | `node --use-env-proxy` con `fetch` vía proxy, petición HTTPS a un mock propio OpenAI-compatible | Fila HTTP `/v1/chat/completions`, sin credenciales ni red externa |
   | Scripts de Python | Dos procesos, uno con `requests` y `REQUESTS_CA_BUNDLE` y el otro con `httpx` y `SSL_CERT_FILE`, contra el mismo mock | Una fila HTTP por proceso; usa los paquetes solo si ya están disponibles, no instales dependencias en el entorno del usuario sin permiso |
   | `curl` | Proceso real, HTTPS al mock, `CURL_CA_BUNDLE` | Una fila HTTP, sin cuenta ni cuota |

   El mock es un servidor HTTPS de prueba en `127.0.0.1`, con CA propia y certificado de origen para `localhost`, montado fuera del repo. Configura `ssl_verify_upstream_trusted_ca` con esa CA pública **solo en el proxy local de scripts**; no desactives la validación TLS. Haz que el cliente conecte a `localhost` **a través** del proxy: quita `NO_PROXY`/`no_proxy` solo en los comandos cliente tras `via.sh`. En la prueba directa usa la CA del mock en vez de la del proxy y no uses `via.sh`. Verifica que una llamada directa al mock no crea fila y que la llamada a través del proxy sí. Devuelve JSON Chat Completions válido, código 200, con `prompt_tokens=10000`, `prompt_tokens_details.cached_tokens=9500`, `completion_tokens=10` y `choices` de texto sintético. Se espera `Leído de caché: 95,0 %` en verde. No simules Claude Code/OpenCode/Copilot con este mock ni cuentes los scripts como clientes de IA autenticados.
3. Después de cada invocación confirmada, captura solo la proyección de su ventana de filas. Si cualquier CLI falla, se excede el presupuesto acordado, un cliente lanza varias peticiones facturables o no hay atribución segura, no lances el siguiente sin consultar al usuario. Si ya hay filas, valida y documenta esas filas aunque el cierre quede bloqueado. No exijas que un proveedor dé un HIT en una prueba de aspecto: el resultado depende de sus cachés internas.
4. Con el proxy aislado todavía en marcha, espera a estado final con un plazo máximo de 10 s tras terminar el cliente. Guarda un manifiesto temporal de **cada fila** de su ventana que terminó `done` con los campos `id`, `verdict`, `label`, `high` e `incremental`. Deriva `label` y `high` del `usage` leído de la API, no del DOM: lee `read` e `input_total` enteros seguros, aplica el 90 % sin redondeo, muestra un decimal con coma (salvo `<90 %` si redondea a `90,0 %` sin alcanzar el umbral); usa `Lectura de caché: sin datos` si no existe un par utilizable. Usa `incremental=true` solo si `context_partial` es `true`. Ejecuta `TAP_UI_PORT=<puerto del panel de prueba> TAP_DEBUG_PORT=<puerto CDP libre> node tests/ui/check.mjs --inspect-cache-read <manifest.json>` y comprueba cuatro combinaciones por fila. Registra filas no completadas aparte, nunca como casos visuales aprobados. Comprueba los importes y cargo reportado solo si disponibles; no inventes ceros ni calcules una factura para un cliente que no la reporta.
5. Escribe `validacion-real.md`: una fila por cliente, versión, perfil/modelo sin identificadores privados, transporte, filas con uso, `%` y veredicto observados, resultados claro/oscuro × escritorio/estrecho, créditos/coste reportados cuando existan, y estado (`pasó` o `bloqueada`, con motivo). Registra el comando exacto del chequeo visual sin variables secretas. Cierra únicamente los procesos, pestañas y recursos temporales de esta prueba; no toques servicios existentes.
