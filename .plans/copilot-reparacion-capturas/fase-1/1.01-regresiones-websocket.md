## Pasos

1. Ejecuta BASELINE. Si no reproduce los valores siguientes, no adaptes expectativas: bloquea.
2. Copia los datos de `casos.json` a la nueva fixture. Conserva su procedencia: son escenarios sintéticos, no una captura real. El test no debe leer `.plans` ni `data/`.
3. Implementa un ejecutor pequeño de los pasos de la fixture en el nuevo test. Usa la petición y usage de la fixture original, copiados antes de sustituir IDs; el log y todo estado de store son temporales. Sigue el aislamiento y limpieza del test de diagnóstico existente.
4. Comprueba esta tabla en el test:

   | Caso | Entrada tras create | Resultado actual fijado |
   | --- | --- | --- |
   | other_same | created A, in_progress B, completed B, close | error/ERR; observe, ignore_other_id, ignore_other_id, fail tras start |
   | other_different | created A, in_progress B, completed C, close | Mismo resultado y diagnóstico completo que other_same |
   | terminal_only | created A, completed B, close | error/ERR; B no termina la captura |
   | matching | created A, in_progress A, completed A, close | done/PARTIAL; usage y coste de la fixture original |
   | wrong_then_correct | created A, completed B, completed A, close | done/PARTIAL; una sola finalización y coste |
   | overlap | created A, segundo create, close | error/ERR; una sola fila y conexión deshabilitada |

5. Para errores, exige ausencia de usage/cost, acumulados vacíos, ningún JSONL escrito y reservas liberadas. Para éxitos, exige usage exacto de la fixture, `usd=0.00064409`, un acumulado priced y una línea de log; no `ws_diagnostic`. En todos, una sola fila y ningún mensaje de entrada mutado.
6. Añade una aserción explícita de igualdad entre los dos diagnósticos other_same/other_different. No añadas un test saltado ni expectedFailure para fingir que la reparación existe.
