## Hechos

- **Observado — diagnóstico local:** las etiquetas `other` no guardan el valor ni la relación entre los IDs. La evidencia local deja explícitas dos secuencias compatibles, `A → B → B` y `A → B → C`.
- **Observado — fixtures sintéticos:** los dos casos producen idénticas acciones (`ignore_other_id`) y el mismo `ERR`; la igualdad de los diagnósticos solo prueba que hoy se pierde esa distinción. No son tráfico real.
- **Observado — proyección local:** `_project_response` conserva `response.id` únicamente cuando es una cadena. `project_event` usa esa proyección para `response.created`, `response.in_progress` y `response.completed`; el campo alternativo de nivel superior `response_id` se contempla solo para delta y errores terminales. No se copia el sobre completo.
- **Observado — procesamiento local:** `_process_server_message` compara IDs explícitos con el ID activo y registra `ignore_other_id` ante discrepancias. Una vez asociado el ID activo, un `response.in_progress` sin ID puede observarse y un delta sin `response_id` puede pasar; un delta con ID distinto se ignora. `response.completed` solo finaliza cuando su ID proyectado coincide exactamente con el ID activo; si falta o difiere, no finaliza. Los errores `response.failed`, `response.incomplete` y `error` siguen su rama separada: solo se ignoran por ID distinto cuando ambos IDs están presentes; si no, se falla la captura según el comportamiento actual. El guard de solapamiento deshabilita la inspección de la conexión.
- **Especificado — límites locales de seguridad:** el protocolo local exige no mezclar respuestas, ignorar terminales del ID ya terminado y detener la inspección ante ambigüedad/solapamiento. Se conservan como restricciones; no prueban una ruta alternativa válida.
- **Observado en una muestra pública, no especificado como invariante:** la referencia de OpenAI ilustra `response.created` y `response.in_progress` con el mismo `response.id`. El ejemplo no prueba que cada terminal de Copilot tenga ese ID ni que un `B` alternativo corresponda al create activo.
- **Especificado para OpenAI, no para Copilot:** la guía actual de WebSocket Mode usa `stream_id` para separar carriles y permite intercalación entre ellos. No se observó evidencia de que el gateway probado exponga tal campo.
- **Observado sobre disponibilidad pública:** el tag oficial de Copilot CLI v1.0.105 existe y ofrece un archivo fuente, pero el árbol público consultado no muestra el código del runtime. No se encontró allí una especificación versionada de la asociación de IDs.
- **Hipótesis no demostrada:** que el `B` de `in_progress` sea el mismo ID que el `B` de `completed`, o que cualquiera de ellos represente el mismo `response.create` identificado por `A`. El mismo rótulo `other` no acredita igualdad, orden causal ni pertenencia.

## Regla candidata

No queda demostrada una regla que permita aceptar el ID alternativo. La condición vigente para finalizar con `response.completed` es que el ID proyectado del evento coincida exactamente con el ID activo asociado en `response.created`; un `response.completed` sin ID o con uno distinto no finaliza. Esta descripción se limita a ese terminal y refleja el guard actual, no una política nueva para otros eventos. En particular, una vez asociado el ID activo, `response.in_progress` puede observarse sin ID y un delta puede pasar sin `response_id`; los errores `response.failed`, `response.incomplete` y `error` conservan su rama vigente, sin inferir aquí una nueva regla. El rechazo de solapamientos y de IDs explícitamente distintos se mantiene. No queda aprobada ninguna ampliación para un ID alternativo.

No aceptar un terminal por orden de llegada, por ser la única petición activa, por repetir una etiqueta `other`, por igualdad aparente de IDs entre mensajes sin vínculo al create, ni por `stream_id` tomado de documentación genérica de OpenAI.

## Contraejemplos

| Secuencia sintética | Resultado guardado actual | Qué demuestra / qué no demuestra |
| --- | --- | --- |
| `created=A, in_progress=B, completed=B` (`other_same`) | `ignore_other_id`, `ignore_other_id`, después cierre `ERR` | **Demuestra** que la implementación actual no rescata ese terminal. **No demuestra** que `B` sea el ID correcto. |
| `created=A, in_progress=B, completed=C` (`other_different`) | El mismo diagnóstico y `ERR` | **Demuestra** que los datos guardados no distinguen el caso anterior. No demuestra que `B`, `C` o ambos pertenezcan al create. |
| `created=A, completed=B` (`terminal_only`; sin `in_progress`) | El terminal no se acepta; cierre `ERR` | La fixture sí incluye `created_a`; prueba que ese terminal explícitamente ajeno no completa. No establece cuál sería una identidad alternativa válida. |
| `created=A, completed=B, completed=A` (`wrong_then_correct`) | Se ignora `B`; el `A` coincidente completa | Es un test sintético de igualdad estricta, no una regla del gateway para terminal tardío o IDs transformados. |
| Segundo `response.create` con captura activa (`overlap`) | La captura activa falla y la conexión queda deshabilitada | El rechazo evita asignar eventos ambiguos a otra fila; no se debe debilitar para resolver IDs alternativos. |

Los casos proceden de `casos.json` y del fixture offline. En ninguno se infiere relación a partir de dos etiquetas `other`, ni se conservan IDs reales.

## Decisión

| Pregunta | Evidencia necesaria para responder sí | Resultado con las fuentes disponibles |
| --- | --- | --- |
| ¿`in_progress` y `completed` comparten ID alternativo? | Relación explícita de igualdad, no dos etiquetas `other`. | **No acreditado.** La muestra de OpenAI tiene el mismo `response.id`, pero es solo un ejemplo de otro servicio; los diagnósticos locales no conservan esos valores. |
| ¿Ese ID pertenece al mismo create? | Campo o transición documentada que lo vincule inequívocamente. | **No acreditado.** La secuencia resumida no retiene el vínculo; no hay una especificación pública de Copilot CLI 1.0.105 con esa transición. |
| ¿Qué hacer con A/B/C, terminal tardío o IDs contradictorios? | Regla negativa que preserve el rechazo sin mezclar `usage`/texto. | **Para finalizar con `response.completed`, preservar la coincidencia exacta exigida actualmente** y no aceptar un ID ajeno o ausente. Los tests fijan guardas sintéticos de mismatch y solapamiento; esta decisión no cambia el tratamiento actual de deltas ni errores. |
| ¿Hay que cambiar la proyección? | Ruta del campo demostrado y su validación exacta; nunca copiar el sobre completo. | **No.** No se ha demostrado una ruta alternativa del gateway. Mantener la validación existente de `response.id` y no añadir campos inferidos. |

**Decisión final — `status=insuficiente`, `approved=false`.** La observación estructural mínima que falta es una especificación oficial versionada del gateway o una observación sanitizada atribuible a CLI 1.0.105 que preserve, para cada `response.create`, las relaciones simbólicas de ID de `created`, `in_progress` y `completed`, la transición que los vincula y el comportamiento ante orden tardío/contradictorio; debe incluir el caso necesario para descartar mezcla con otra petición. No se necesitan ni deben conservarse IDs reales, cabeceras, cuerpos, texto, usage ni contenido privado. Esta tarea no instrumenta producción ni autoriza otra llamada.
