# 2.03 Gestionar el camino correcto de una sesión secuencial

**Objetivo:** Convertir los creates y terminales Responses en registros separados, sin mezclar turnos.

**Lee:** `cachetap/websocket.py`: decoder/proyección; `cachetap/capture.py`: API común; `tests/fixtures/copilot_responses_ws.json`; `protocolo.md`: «Estado por conexión y límites», especialmente correlación y contexto parcial.

**Puedes tocar:** `cachetap/websocket.py`, `tests/test_websocket.py`.

## Pasos

1. Implementa `Session(host, path, logger)`, con métodos client(content, at), server(content, at) y close(at=None). No recibe objetos mitmproxy ni realiza red. Guarda una captura activa, su timestamp de cliente y como máximo ID activo/último: nada de historiales de eventos o IDs.
2. En un response.create válido llama begin y start. El cuerpo retenido es la serialización de la petición normalizada; req_bytes conserva la longitud original del mensaje. Usa transport websocket y activa context_partial si previous_response_id es texto no vacío.
3. La reserva se adquiere en cuanto se acepta el create: status 101, resp_headers vacío, request_end igual al timestamp del mensaje cliente y response_start None; no hay hdr_s.
4. Alimenta únicamente las proyecciones permitidas, serializadas como SSE interno, mediante capture.feed con at. El razonamiento y los eventos de herramientas no generan texto ni TTFT.
5. Vincula response.created con el ID activo y finaliza el completed correspondiente exactamente una vez. Ignora eventos sin petición activa, terminales duplicados y terminales del último ID terminado. No permitas que un ID distinto finalice una petición ya identificada.
6. close falla una activa con mensaje local fijo, libera recursos y olvida el estado. Puede llamarse repetidamente. No depende de HTTPFlow.
7. Añade esta cobertura del camino correcto:

   | Caso | Resultado esperado |
   | --- | --- |
   | Fixture completo | Una fila con transport websocket, status 101, PARTIAL, uso/texto/TTL/coste iguales a expected; una línea de log y CONV_TOTALS priced=1 |
   | Cliente T, deltas T+0,5 y T+0,8, terminal T+2 | ts=T, ttft_s=0.5, total_s=2.0; sin hdr_s |
   | Dos creates completos secuenciales con IDs distintos | Dos filas y finalizaciones; texto/usage no se mezclan; la segunda admite otro timestamp de origen |
   | Terminal duplicado / ID terminado / close repetido | No crecen log, filas ni total; reservas vacías |
   | Otro ID durante activa identificada | La activa no termina ni cambia de usage |
   | previous_response_id no vacío | Registro N/A con nota de contexto parcial; sin enlace o pérdida inventados |
   | Razonamiento entre deltas | No aparece en output, raw_usage ni log; no adelanta el TTFT |
   | Delta vacío antes del primer texto | No adelanta TTFT; se siguen contando sus bytes originales |
   | Fin con petición activa pero sin terminal | ERR y liberación de recursos |

8. No conectes hooks todavía. La siguiente tarea completa las defensas del estado antes de que este código procese tráfico real.
