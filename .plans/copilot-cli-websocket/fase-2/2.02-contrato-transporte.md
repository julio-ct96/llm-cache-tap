# 2.02 Preparar el contrato común para el nuevo transporte

**Objetivo:** Admitir metadatos WebSocket, contexto parcial y finalización idempotente sin cambiar HTTP.

**Lee:** `cachetap/capture.py`: API completa; `cachetap/record.py`: Record, CaptureLimit; `cachetap/verdict.py`: judge; `cachetap/store.py`: count_cost; `tests/test_record.py`; `tests/test_verdict.py`: JudgeTest; `protocolo.md`: «API común de captura» y filas de contexto parcial en «Estado por conexión y límites».

**Puedes tocar:** `cachetap/capture.py`, `cachetap/record.py`, `cachetap/verdict.py`, `tests/test_capture.py` (nuevo), `tests/test_record.py`, `tests/test_verdict.py`.

## Pasos

1. Añade los campos opcionales `transport: Literal["websocket"]` y `context_partial: Literal[True]` a Record, sin defaults HTTP. No añadas valores nuevos a Verdict ni a CaptureLimit.
2. Amplía begin con las keywords `transport=None` y `context_partial=False`, feed con `at=None`, finish y fail con `ended_at=None`. Sigue las firmas de `protocolo.md`; los defaults conservan exactamente el resultado HTTP actual.
3. En begin solo añade transport cuando se suministre; solo añade context_partial cuando sea True. Para contexto parcial no busques previa, crea conversación nueva y deja `_msgs=[]` para que ninguna futura petición se enlace con ella.
4. En judge, después de la comprobación de ausencia de usage, aplica el N/A y la nota exacta del contrato si context_partial. No añadas causas de MISS ni coste perdido.
5. Añade `closed=False` al estado interno. finish y fail marcan closed y liberan recursos incluso si ya no existe el registro; si estaba cerrado, no vuelven a publicar, loguear ni sumar coste. limit también es idempotente. El flag no forma parte del registro público.
6. Añade los tests del contrato; prepara store y log temporal en cada test:

   | Entrada | Resultado esperado |
   | --- | --- |
   | begin sin keywords nuevas | Registro sin transport ni context_partial; replay histórico idéntico |
   | begin con transport websocket | Campo transport presente; mismo resto del análisis |
   | Contexto parcial y usage válido del fixture | N/A y nota `contexto incremental WebSocket: no se dispone del prefijo completo`; prev_id None, sin lost_usd |
   | Contexto parcial sin usage | Nota existente `la respuesta no trae usage` |
   | Petición completa posterior con mensajes iguales a una parcial | No se enlaza con la parcial, cuyos `_msgs` están vacíos |
   | Reloj cliente T, feed de deltas en T+0,5 y T+0,8, finish T+2 | `ttft_s=0.5`, `total_s=2.0` usando los timestamps explícitos |
   | finish dos veces y luego fail sobre el mismo estado | Una línea de log, una finalización y CONV_TOTALS priced=1; chunks y reservas vacíos |
   | fail dos veces; finish después de expulsión | Sin duplicados ni resurrección; liberación completa |

7. Usa el caso fixture para los tests de uso y coste, no inventes una tarifa. No conectes todavía Session ni los hooks WebSocket.
