# 2.05 Conectar los hooks WebSocket de mitmproxy

**Objetivo:** Que la llamada real del CLI cree una fila sin convertir el handshake ni `/auto` en inferencias.

**Lee:** `tap.py`: todos los hooks, recarga y `LLM_PATHS`; `cachetap/websocket.py`: Session y uninspectable; API instalada `mitmproxy.websocket.WebSocketMessage` y `WebSocketData`; `protocolo.md`: «Frontera mitmproxy».

**Puedes tocar:** `tap.py`, `tests/test_websocket_hooks.py` (nuevo).

## Pasos

1. Añade el import con prefijo de `cachetap.websocket` y `SOCKETS`, tipado por ID de flow. Implementa `websocket_start`, `websocket_message` y `websocket_end` exactamente con las condiciones del contrato.
2. Deja intactos `_is_llm` y `LLM_PATHS`. No leas cabeceras HTTP de petición para detectar upgrades: usa método, ruta, host, status 101 y `flow.websocket`.
3. Procesa solo `flow.websocket.messages[-1]`, ya ensamblado. Ignora mensajes dropped/injected y flows ajenos. Los mensajes binarios activos llaman `Session.uninspectable`; no conviertas bytes binarios a texto.
4. Al cerrar o recibir `error`, retira el estado de ese flow y llama close una sola vez. En done cierra y vacía las sesiones antes de parar dashboard, y conserva la limpieza de reservas HTTP.
5. Construye tests con HTTPFlow, Request.make, Response.make, WebSocketData y WebSocketMessage reales de mitmproxy, sin conexiones. Usa timestamp explícito y alimenta los eventos del fixture. No amplíes los fakes del replay histórico ni lo regeneres. Expón en este fichero el helper `play_fixture()` para la cobertura de API: no resetea store, ejecuta el fixture completo y websocket_end, y devuelve el par `(flow, rid)` de la única fila creada; el llamador prepara/reseteará el store y el log temporal.

   | Caso | Resultado esperado |
   | --- | --- |
   | POST `/auto`, luego GET `/responses` 101, luego fixture WS | Ninguna fila por /auto/handshake; exactamente una por create |
   | Dos inferencias en la misma WebSocket | Dos filas; no una sola fila por conexión |
   | Ruta `/v1/responses?x=1` y barra final | Misma aceptación, ruta almacenada sin query |
   | Host raíz/subdominio Copilot | Aceptado; `evilgithubcopilot.com` y `githubcopilot.com.evil.example` no aceptados |
   | Otro host, otra ruta, status distinto o sin websocket | Sin sesiones ni filas |
   | Mensaje inspeccionado | `content`, `dropped`, `injected` e historial de mensajes iguales antes y después |
   | Dos conexiones activas | Estados independientes; cierre de una no toca la otra |
   | Error, websocket_end y done | SOCKETS vacío donde corresponda, sin reservas ni coste duplicado |
   | HTTP POST existente | Sigue pasando la red de seguridad de fase 1 |

6. Verifica que el cuerpo retenido no contiene `headers` raíz ni el sentinel. Nunca introduzcas un volcado de debug de flow o de evento.
