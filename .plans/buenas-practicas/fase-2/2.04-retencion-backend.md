# 2.04 Retención por bytes y eventos de expulsión

**Objetivo:** cuerpos y registros respetan el presupuesto y comunican su expulsión a los clientes.

**Lee:** `cachetap/store.py` completo; `cachetap/config.py`; `tap.py` (`request`); `cachetap/dashboard.py` (`_events`); `tests/test_store.py`; `tests/test_eviction.py`; `tests/test_dashboard.py` (`test_events`); `tests/replay/adapter.py`; `contratos.md` (Límites y Expulsión).

**Puedes tocar:** `cachetap/config.py`, `cachetap/store.py`, `cachetap/dashboard.py`, `tap.py`, `tests/replay/adapter.py`, `tests/test_store.py`, `tests/test_eviction.py`, `tests/test_flows.py`, `tests/test_dashboard.py`.

## Pasos

1. Añade MAX_REQUEST_BYTES y MAX_BODY_BYTES según el contrato. En request comprueba bytes antes de `get_text`; las peticiones mayores se dejan pasar sin captura y con warning fijo.
2. Mantén bytes retenidos en `STATE['body_bytes']`; resetea en clear y adapter.reset. `add` descuenta reemplazos de ID antes de sumar y devuelve expulsados.
3. Implementa el protocolo de `push` del contrato y pasa los expulsados desde request. Añade max_records al snapshot de `_events`.
4. Ajusta el test de eviction: siguen siendo cinco logs y quince eventos; los record events de las peticiones cuarta/quinta incluyen expulsados 1/2. El escenario normal no recibe propiedades nuevas.

| Caso nuevo | Resultado |
| --- | --- |
| Presupuesto 4 bytes, cuerpos `ñ`, `ab`, `c` | IDs 2,3 retenidos; contador 3; expulsa 1 |
| Clear tras retención | Contador cero, ambos mapas vacíos |
| Reemplazar mismo ID | Se descuenta su cuerpo anterior; sin doble conteo |
| Cuerpo único mayor que presupuesto | Mapas vacíos y evento `evict`; no reinserción |
| Petición de MAX_REQUEST_BYTES / +1 | Capturada / ignorada; bytes transmitidos intactos |
| Snapshot HTTP | `max_records` coincide con config.MAX |
